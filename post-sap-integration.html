Integrating SAP OData Services with Modern Web Applications

Practical lessons from connecting Next.js frontends to SAP backends — handling authentication, data mapping, error strategies, and real-time sync challenges.

If you've worked in enterprise software, you've likely encountered SAP. It's the backbone of many large organizations' operations — handling everything from supply chain to finance. But its age means connecting SAP to modern web applications requires bridging a significant technological gap. OData (Open Data Protocol) is SAP's preferred interface for this bridge, and I've spent considerable time learning its quirks.

What is SAP OData?

OData is a REST-based protocol that SAP uses to expose its business data and processes. Think of it as a standardized way to query and manipulate SAP data over HTTP. In theory, it's straightforward — GET, POST, PUT, DELETE with familiar JSON or XML payloads. In practice, SAP's OData implementation has its own conventions.

The Integration Architecture

Here's the architecture we settled on after several iterations: 

┌─────────────────┐      ┌──────────────────┐      ┌─────────────┐
│  Next.js Client │ ───▸ │  Node.js Backend │ ───▸ │  SAP System  │
│  (React SPA)    │ API  │  (Express/Proxy)  │ OData│  (S/4HANA)  │
└─────────────────┘      └──────────────────┘      └─────────────┘
                               │
                               ▼
                         ┌───────────┐
                         │   Redis   │
                         │  (Cache)  │
                         └───────────┘

The key decision was adding a Node.js middleware layer instead of calling SAP OData directly from the frontend. This gave us:

  • Authentication abstraction — SAP credentials never reach the browser
  • Response transformation — SAP's verbose response format is mapped to clean DTOs
  • Caching — Frequently-read master data is cached in Redis
  • Error normalization — SAP error codes are translated to user-friendly messages

Authentication Challenges

SAP OData services typically use Basic Auth or OAuth 2.0 (via SAP's XSUAA). Both have their complications. Basic Auth requires careful credential management and session handling. OAuth requires navigating SAP's token flow, which includes CSRF token requirements on write operations.

Our approach: a dedicated authentication service that handles token lifecycle, automatic renewal, and credential rotation without any of this complexity leaking into the business logic layer.

Data Mapping Strategies

SAP data models and modern frontend data models rarely align. SAP uses its own naming conventions (MATNR for material number, BUKRS for company code), while your React components expect clean, readable property names. We built a mapping layer: 

// SAP to Frontend mapping
const materialMapper = {
  toFrontend: (sapData) => ({
    id: sapData.Matnr,
    name: sapData.Maktx,
    category: sapData.Mtart,
    unit: sapData.Meins,
    price: parseFloat(sapData.Stprs),
    currency: sapData.Waers,
    lastModified: new Date(sapData.Laeda),
  }),

  toSAP: (frontendData) => ({
    Matnr: frontendData.id,
    Maktx: frontendData.name,
    Mtart: frontendData.category,
    Meins: frontendData.unit,
  }),
};

Handling Batch Operations

OData supports batch requests — sending multiple operations in a single HTTP call. This is essential for performance when you need to create or update multiple records. SAP's batch implementation uses multipart/mixed content type with changeset boundaries, which is unusual but well-documented.

Lessons Learned

  1. Test with real SAP data early. Mock data will hide encoding issues, null handling edge cases, and performance characteristics.
  2. Cache aggressively. Master data (materials, customers, organizational units) changes infrequently but is queried constantly.
  3. Log everything. When something goes wrong in SAP integration, you need the full request/response cycle to debug.
  4. Handle timeouts gracefully. SAP systems can be slow under load. Your frontend should degrade gracefully, not freeze.
